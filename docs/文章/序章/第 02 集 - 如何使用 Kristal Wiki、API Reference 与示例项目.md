# 第 02 集：如何使用 Kristal Wiki、API Reference 与示例项目

你好呀。这是《从零做一个 Deltarune 同人游戏》系列的第 2 集。

（上一集的番外 EX00 是给 Linux 和安卓读者的，跳过的同学现在回来——本集所有平台通用。）

上一集我们把开发环境搭好了。这一集不写代码，但可能是整个系列里性价比最高的一集：**学会自己查资料**。

先把核心观点说清楚：**Kristal 的 wiki 不是教科书，没有人需要从头到尾把它读完——它是字典，缺啥查啥**。硬啃文档是最低效的学习方式；带着问题来查，才是文档的正确打开方式。本集就用两个真实的问题示范怎么查：

- 在游戏里看到一个存档点——它是怎么来的？
- 想 ban 掉敌人的攻击伤害——怎么做到？

## 认识三种资料

动手之前，先分清手上有哪几类资料，它们各管一摊：

- **Wiki**（[kristal.cc/wiki](https://kristal.cc/wiki/)）：讲"**怎么做**"的教程集。事件怎么放、地图怎么画、文本怎么写，按主题组织成一篇篇指南。
- **API Reference**（[kristal.cc/api](https://kristal.cc/api/)）：讲"**这个功能是什么**"的字典。引擎里所有的类、方法、参数，从源码注释自动生成，按类型整理。
- **示例项目**：讲"**别人怎么写的**"的活标本。真实的目录结构、真实的调用方式，比任何抽象描述都直观。

另外，对国内读者，Wiki 有我的中文翻译：[Shadow-ZH-Fork](https://bli-aik.github.io/Shadow-ZH-Fork/zh/wiki/)——文翻质量勉强说得过去（第 00 集提过），看得懂英文的话还是以官方为准。

## 阅读 Wiki：存档点是怎么来的

假设你在游戏里看到了那个星星——存档点。它是怎么来的？

第一步，把"现象"拆成"关键词"：存档点，英文 savepoint。然后想：它属于哪一类内容？它不是代码逻辑，而是地图上的东西——所以去 Wiki 里找**地图/事件**相关的教程。

Wiki 的导航页（"项目创建"那一页）列着所有教程：设计地图、地图图层、使用事件、过场动画……"使用事件"（using-events）听起来就对。

进去之后你会看到一张大表：一堆事件的名字（可交互对象、脚本、宝箱、传送门……）。往下翻，找到**存档点（savepoint）**一节。读一下，答案就全了：

> 要创建这个 Event，请在 `objects` 图层上定义一个**点**或**单瓦片区域**，并将其命名为 `savepoint`。

就这么简单。存档点是 `Interactable` 的子类，还继承了一堆属性可以调：`marker`（重生标记——玩家死后从这里复活）、`simple`（简单版存档点，没有招募和储物菜单）、`heals`（交互时是否回血，默认 true）……

注意，这一节开头其实还留了一句话："请先阅读设计地图，因为本教程会帮助你理解 Kristal 中的所有事件。"这就是教程的**前置提示**——顺着它走，基础就不会缺。查一个点，顺手把相关的线也看了，这是 wiki 的正确使用姿势。

再往下翻，这一节还带了一个**示例**——照着抄一遍，一个能用的存档点就出来了。这也是 wiki 教程的常态：先讲怎么做，再给你一个能跑的样板。别嫌"抄"丢人，第一遍抄，第二遍改，第三遍就是自己的了。

## 阅读 API Reference：怎么 ban 掉伤害

第二个问题：想 ban 掉敌人的攻击伤害，怎么做？

这个问题 Wiki 教不了——它太具体了，属于"引擎内部怎么算"的层面。这种时候去 API Reference。

先想清楚关键对象：敌人被攻击时，引擎会计算伤害。算伤害的方法挂在哪个类上？敌人——`EnemyBattler`。在 API 站里找到 EnemyBattler，搜伤害相关的词，你会看到一个方法：

```lua
function EnemyBattler:getAttackDamage(damage, battler, points)
```

它的注释会告诉你三件事：这是一个 **Override**（可重写）方法；默认行为是"如果 `damage` 大于 0 就原样返回，否则用攻击者的攻击力和命中点数 `points` 算伤害，再减去自己的防御"；参数分别是伤害值、攻击者、命中点数（最高 150）。

到这里，答案已经出来了：**重写这个方法，让它永远返回 0**。比如我们的 Dog Battle 里，神烦狗就是这么做的：

```lua
-- The dog dodges every attack instead of taking damage.
function Dog:getAttackDamage(damage, battler, points)
    return 0
end
```

所以那条狗为什么砍不动？因为这一行。你看，一个"想 ban 伤害"的需求，走到最后就是重写一个方法、返回一个 0。

顺带一提，API Reference 的内容其实就长在源码的注释里（LuaDoc，`---@param` 那种格式）——官方 API 站是从源码注释自动生成的。所以如果你手边有引擎源码（第 01 集克隆过），直接翻 `src/engine/game/battle/enemybattler.lua`，能看到一模一样的信息，而且还能顺带看它旁边的其他方法。文档会骗人（过时），源码不会。

## 观察示例项目：thrash-machine

第三种资料：示例项目。你不是已经有一个了吗？——thrash-machine（第 01 集建的）。你甚至已经和它的训练人偶打过一架了（往右走进 room2 那个），现在来看看它背后长什么样。

打开它的 `scripts/` 目录，你会发现里面的组织方式和 Wiki 讲的完全对应：

- `scripts/battle/`：战斗相关，下面再分 `enemies`（敌人）、`encounters`（遭遇战）、`waves`（弹幕回合）、`cutscenes`（战斗演出）、`bullets`（子弹）……
- `scripts/data/`：数据类脚本，`actors`（角色）、`items`（物品）……
- `scripts/world/`：世界相关，`maps`（地图）、`cutscenes`（过场）……
- `assets/`：素材；`libraries/`：库。

随便打开一个文件看真实写法——比如 `scripts/battle/enemies/dummy.lua`（训练人偶）：它定义了一个 `Class(EnemyBattler)` 的类，`init` 里设置血量、攻击力、ACT 选项，`onAct` 里写各个 ACT 的效果。你在 Wiki 上学到的"敌人怎么写"，在这里能看到完整的真实形态。

观察示例项目有个要点：**不要只看某一个局部，先看目录再看到文件**。目录告诉你是"什么"，文件告诉你是"怎么写的"。把两者对应起来，你就理解了这个项目的骨架——之后自己加内容，就知道该往哪放。

## 把需求转换成查找路径

两个例子走完，回头看通用的方法。一个"想实现的效果"要变成"查到的资料"，中间就三步：

1. **拆关键词**：效果 → 名词。存档点 → savepoint；ban 伤害 → damage。
2. **判断类型**：它是"怎么做"（教程类）还是"是什么"（功能类）还是"别人怎么写"（示例类）？
3. **选对入口**：教程类 → Wiki 对应主题页；功能类 → API Reference 找对象；写法类 → 示例项目找同类文件。

来点实战预演——把第 00 集"项目事实"里的需求映射一下：

- "想给敌人加一个讲笑话的 ACT" → Wiki 的敌人/遭遇战教程 + thrash-machine 的 dummy.lua 看 ACT 写法；
- "想做一个会移动的弹幕" → Wiki 的弹幕教程（wavemaking）+ 示例项目的 `waves/` 目录；
- "想让敌人被攻击时有特殊反应" → API Reference 的 EnemyBattler（你会发现 `onHurt` 之类一堆可重写的方法）；
- "想让游戏启动后直接进入战斗" → Wiki 的创建项目教程（mod.json 那一节，`encounter` 字段）——我们的 Dog Battle 就是这么配的。

你会发现大多数需求，走这三步都能落到某个具体页面或文件上。

## 记录和验证结果

查到了，别急着信——**回项目里验证**。改一行代码，`Ctrl+R` 热重载（第 01 集教的），看行为是否符合文档说的。验证的方式分两种：简单的小改动，直接跑起来看行为对不对；涉及数值的，可以开调试控制台（第 00 集提过的反引号控制台），输个 `=变量名` 直接看实际值。行为和值都对上了，这条资料才算真正到手——文档可能过时、可能省略细节，验证过的东西才是你的。

另外养个习惯：把查到的来源和结论记下来（一个笔记文件、甚至就是注释）。同一个问题，下次就不用从头再查一遍——你会发现"查资料"这件事，查过一次的问题会越来越少。

## 结尾

这一集的核心就一句话：**缺啥查啥，查完验证，验证完记录**。文档是工具，不是门槛。
